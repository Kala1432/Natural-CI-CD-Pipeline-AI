# Deployment Architecture - CI/CD Pipeliner

This document describes the deployment architecture and strategy for hosting the CI/CD Pipeliner platform itself, as well as the mechanism it uses to deploy user applications.

## 1. Hosting CI/CD Pipeliner (The Platform)

### Infrastructure Components
*   **Web Server / Reverse Proxy:** Nginx (handles HTTPS termination, static file serving for the React frontend, and reverse proxies API requests to the backend).
*   **Backend Application Server:** Gunicorn running the Flask application (WSGI).
*   **Task Workers:** Celery workers running in background processes.
*   **Message Broker & Cache:** Redis.
*   **Database:** PostgreSQL (Managed service like AWS RDS is recommended for production).
*   **Storage:** AWS S3 (for logs, generated artifacts, and large ML model weights).

### Docker Containerization
The entire platform is containerized using Docker Compose.
*   `frontend` container: Nginx serving the static Vite build.
*   `backend` container: Flask API.
*   `worker` container: Celery workers executing background tasks.
*   `redis` container: Redis instance (if not using a managed service like AWS ElastiCache).
*   `db` container: PostgreSQL instance (if not using RDS).

### Platform CI/CD
The CI/CD Pipeliner repository uses its own generated GitHub Actions workflow to build, test, and deploy itself to the production AWS EC2 instance. Secrets are managed via GitHub Actions Secrets.

## 2. Deploying User Applications (The Product Feature)

When CI/CD Pipeliner generates and deploys a user's application, it follows this architecture:

### Target Environment
*   **AWS EC2:** CI/CD Pipeliner primarily targets AWS EC2 for user application deployments.
*   **Authentication:** The backend uses secure IAM roles or AWS OIDC integration to authenticate with AWS, rather than long-lived static access keys.

### Deployment Workflow
1.  **Trigger:** A merged Pull Request in the user's GitHub repository triggers a GitHub Actions workflow (generated by CI/CD Pipeliner).
2.  **Build & Push:** The workflow builds a Docker image and pushes it to a container registry (e.g., Docker Hub or Amazon ECR).
3.  **Webhook Notification:** The GitHub Action sends a webhook to the CI/CD Pipeliner `/api/deploy` endpoint.
4.  **Provisioning / Update:** A Celery worker connects to the target EC2 instance via SSH or AWS Systems Manager (SSM).
5.  **Execution:** The worker pulls the new Docker image and runs it (using `docker run` or `docker-compose`).
6.  **Health Check Loop:** The `Deployment Monitoring Module` begins polling the application's health endpoint.

### Automatic Rollback
If the health check fails within a specified timeout (e.g., 5 minutes):
1.  The Celery worker identifies the failure.
2.  The worker stops the failed container.
3.  The worker restarts the previously running container image.
4.  An Incident is generated in the CI/CD Pipeliner dashboard.
