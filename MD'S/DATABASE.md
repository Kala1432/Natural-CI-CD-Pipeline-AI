# Database Schema - CI/CD Pipeliner

This document outlines the core relational database schema managed by SQLAlchemy and PostgreSQL.

## Core Entities

### User & Authentication
*   **User:** Core identity entity. Stores email, hashed password, role (user/admin), and account status.
*   **GithubConnection:** Links a `User` to a GitHub identity and stores OAuth/App installation IDs.
*   **EmailOTP:** Stores hashed One-Time Passwords for email verification.
*   **UserProfile:** Stores non-critical user preferences and notification settings.

### Repository & Project
*   **Project:** Represents a user-connected repository. Tracks `repo_url`, `default_branch`, and analysis `status`.
*   **AutomationStep:** Represents a discrete CI/CD step recommended by the analyzer (e.g., Lint, Test, Docker Build). Links to `Project`.

### Workflow Generation
*   **GeneratedWorkflow:** Stores the actual YAML/Dockerfile content generated by the AI for a specific `Project`. Tracks PR status (`draft`, `open`, `merged`).
*   **SimulationRun:** Tracks the status of local validation/simulation of the generated workflow before creating a PR.

### Deployment & Monitoring
*   **Pipeline:** Represents a specific execution of a CI/CD pipeline (triggered by GitHub).
*   **Deployment:** Represents an attempt to deploy a built artifact to a target environment (EC2). Links to a `Pipeline`. Tracks `status` (pending, success, failed, rolled_back).
*   **CloudDeployment:** Stores AWS specific metadata (instance IDs, health endpoint URLs).

### Observability
*   **ErrorReport / Incident:** Logs system errors, deployment failures, or anomalies detected by the ML engine.
*   **Analytics:** Stores aggregated metrics for dashboards.
*   **AIPrediction:** Stores the results of ML failure predictions for pipelines.
*   **AuditLog:** (To be implemented) Immutable ledger of critical actions.

## Schema Conventions
*   All tables use an auto-incrementing integer `id` as the primary key.
*   Foreign keys enforce referential integrity with cascading deletes where appropriate (e.g., deleting a User deletes their Projects).
*   `created_at` and `updated_at` timestamps exist on all mutable records.
*   Soft deletes should be implemented for Projects and Users in the future to preserve audit trails.
